# WDP301-188 — Amenity management UI

## Scope and approved prototype gaps

The user approved keeping the existing images, descriptions, room-type relationships and counts, activity filter, and deactivate/reactivate actions in the prototype table/dialog presentation. Category management and deletion are excluded. The accessible heading, field and action names, hooks, API calls, validation, permissions, routes, search debounce, and server pagination remain in place.

The page reuses `PageContainer`, `PageHeader`, `DataTable`, atomic controls and badges, and the existing loading/error/empty presentations. The editor reuses `Dialog` and `AlertDialog`, retaining its confirmation messages, pending-save dismissal lock, and focus restoration. Direct state toggles still send only `isActive`; regular saves still send only changed metadata and the complete selected relationship set when it changes. A single supported image may replace the current image, and upload retries retain successful uploads as before.

The retained `ImagePicker` helper has an optional `appearance="prototype"` presentation. Its default appearance and callbacks remain available to the unmigrated service form. The new variant is tested and documented in `DESIGN.md`; no package or new flat component was added.

## Test evidence and assertion changes

- Baseline: the 31 existing amenity tests passed before production changes.
- A new unchanged-edit regression also passed against the original implementation.
- Before implementation, three tests failed at the expected points: prototype image-picker classes and the two accessible confirmation dialogs. The other 19 tests in that run passed.
- After implementation, all 36 tests in the amenity and image-picker suites passed.
- Confirmation tests use the shared `AlertDialog` instead of mocking `window.confirm`. The editor test sends Escape instead of a native cancel event and waits for dialog removal/focus restoration. The pending-save test also tries the new close button.
- The table assertion waits for a loaded row because the prototype table exists during skeleton loading. Pagination text follows the shared `Trang 2 / 3` display.
- Additional tests preserve unchanged edits, checkbox state changes with draft metadata/relationships, the legacy image-picker default, the prototype empty presentation, long image labels, and choose/remove callbacks.

## Limitations and exceptions

- No backend, hook, route, API contract, or dependency was changed. Backend checks and database write tests are outside this presentation-only change.
- Browser verification uses read-only QA fixtures through the normal API client/auth provider. Request payloads, validation, and upload sequencing are tested separately. No manual screen-reader session is claimed.
- The final production build uses `npm run build` in a clean source copy with the existing dependencies. The changed production files must match the copy byte for byte. This avoids the previously locked `frontend/dist` and excludes unrelated user Vite configuration edits without deleting existing files.
- The approved prototype gaps and screenshot-upload waiver are recorded above. Prototype mock data, category fields, deletion, and the prototype-only save notice are not shipped.
- The pre-existing user edits remain outside the ticket commit.
